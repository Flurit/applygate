# Policy

`policy.Decide` analyzes the tool call, classifies each operation it would start, resolves an environment tier for each one, runs preflight and (for saved plans) the plan gate, and returns the strictest verdict. Every ask or block carries the reason, the evidence and a next step.

## Decision flow

1. The hook adapter turns the agent's event into one internal event: agent, tool, command or paths, working directory, session, and whether the host can show an ask prompt.
2. `internal/shell` parses the command as bash and walks it in order. It tracks `cd`, assignments, `export`, prefix assignments, loops over literal lists, functions with positional parameters, aliases, and `$0` in scripts. It unwraps `bash/sh/zsh -c`, `eval`, `source`, credential and secrets runners (`aws-vault exec`, `aws-okta exec`, `gds aws`, `saml2aws exec`, `aws-sso exec`, `envchain`, `doppler run`, `op run`, `chamber exec`, `infisical run`, `dotenvx run`, and the command string of `doppler`/`infisical run --command` and `sops exec-env`/`exec-file`; the profile or role they name counts as the AWS profile), development-environment runners (`direnv exec`, `mise`/`rtx exec`, `asdf exec`, `devbox run`, `nix develop|shell -c`, `nix-shell --run`), wrappers listed under `wrappers:` in the config, here-documents and here-strings, pipes into a shell, `sudo`, `env` (including `-C` and `-S`), `timeout`, `nice`, `nohup`, `xargs`, `watch`, `find -exec`, `ssh`, `docker run <terraform image>`, Makefile recipes and readable shell scripts. It computes static output for echo, printf, cat, base64 -d, base32 -d, gzip/gunzip/zcat, tee, xxd -r -p, rev, dirname, basename, pwd and which. Whatever it cannot resolve becomes a **problem** (dynamic), not a guess: a word the shell would expand against the disk or locale (an unquoted glob, zsh's `=name`, `$'\u…'`), a variable assigned at run time (`read`, `printf -v`, `mapfile`, `declare -n`), a placeholder with unknown input (`xargs -I`, `parallel`), interpreter code built from variables, and a file an earlier step of the same command writes (a script, a sourced file, `$(cat f)` input, a makefile). Program names are compared without case, and shell builtins with it. A background statement runs on a copy of the state, a function body in the caller's shell. The commands programs run through their own options are analyzed (git aliases and `rebase -x`, `ssh -o ProxyCommand`, `flock -c`, `su -c`, `conda run`, `nix run`, `env -S`). A parse error, an exhausted budget or a lost directory is judged at the most protected tier under the repository root (step 4). Code given to `python`/`node` (`-c`/`-e`, a here-document, a script file) is not parsed; it is a problem only when its text mentions an infrastructure tool, an AWS SDK or a guard file, and a Python or Node body that does so but can only read and write ordinary files (no process start, code loading, network, decoder, function passed by reference or guard, credential or state file named anywhere in it, and every write to a literal path that resolves to a repository configuration file under the working directory, by the rules in [limits.md](limits.md)) is instead recorded as a note and allowed. For a program it does not recognize, a backstop treats a standalone `terraform`, `tofu` or `terragrunt` argument as the start of the command the program runs (`madeup-tool run -- terraform destroy`), and so the value of a `--run`/`--command`/`-c` flag that starts with one. It skips text and search programs, version control, editors, package managers, quoted strings and the values of message flags (`-m`, `--message`, `--title`, …), and drops unknown Terraform subcommands it reaches that way (`brew install terraform tflint`).
3. `internal/classify` assigns a class to each invocation, redirect and file tool call. **Strict shapes** (`strict_shapes`, on by default; only the user config can turn it off) add one more action to a shell command that is not plain: one that does not parse, uses any construct other than simple commands joined by `&&`, `||`, `|` or `;` (functions, `$(…)`, `$((…))`, `let`, loops and conditionals, subshells, `[[ ]]`, declarations such as `export`, `${x:-…}` and other non-plain parameter expansions, `$'…'`, background or negated statements), has a part the analyzer could not resolve, sets a variable that is not on a short safe list, or runs a program whose call does not fit its **exact shape**.
   - **Exact shapes** (`internal/shell/shapes.go`) say, for each program, which calls cannot run another program: the subcommands and options it may use, or "any arguments" for a program with no such option (`ls`, `cat`, `grep`, `terraform`). Examples: `git` without `-c`, `-p`, `--upload-pack`, `--exec`, `ext::` URLs or subcommands outside its list; `tar` with its usual create, extract and list options only; `sed` scripts without the `e`, `w` and `W` commands or the `e` and `w` flags; `kubectl` and `helm` without plugins, another kubeconfig or a post-renderer; `go` only for `version`, `env`, `list` and `doc`. A program with no shape is not plain: shells, interpreters, most wrappers (`bash -c`, `python3`, `xargs`, `timeout`, `nohup`), package managers and runners (`npm`, `npx`, `pip`, `cargo`, `brew`, `pre-commit`) and pagers (`man`, `less`). A wrapper counts as the program it runs, and a `make` recipe's programs count too.
   - **Variables:** a variable the command sets for a program (`X=1 cmd`, `env X=1 cmd`), or an upper-case one it sets in the shell, must have a literal value and a name on the safe list (`AWS_PROFILE`, `AWS_REGION`, `TF_LOG`, `TF_WORKSPACE`, `TF_VAR_*`, `LC_*`, `NO_COLOR`, …); `PAGER`, `GIT_PAGER` and `AWS_PAGER` may only be empty or `cat`. A lower-case shell variable (`d=/tmp/x`) is local and plain.
   - **Repository state:** a git command is plain only when its repository has no hooks (other than `*.sample`) and its config (`.git/config`, `config.worktree`) sets no key that runs a command: `core.fsmonitor` other than a boolean, `core.hooksPath`, `core.pager`, `core.editor`, `core.sshCommand`, `alias.*` starting with `!`, `remote.*.uploadpack`, `filter.*`, `diff.*.textconv`, `include.path`, `ext::` URLs and the like. A command that names a path in a git directory's hooks or config is not plain either, since the git command after it would run what it wrote. The action is of class `complex-shape`, judged in each directory the command runs in: it asks in a protected environment and is allowed elsewhere. It catches constructs that make the shell run code the analyzer does not follow, such as an exported function, arithmetic on a variable holding `$(…)`, `PS4` under tracing and `BASH_ENV=/dev/stdin` (red-team round 4, 4C1 to 4C4). Measured on the agent trial's 162 real calls, it asks about 29 (18%) more in a protected directory ([review/v0.6.0/2026-11-03-strict-shapes.md](../review/v0.6.0/2026-11-03-strict-shapes.md) has the earlier measurement).
4. For each action, the tier comes from config (paths, workspaces, backends, AWS profiles, optional accounts, and for `kubectl`, `helm`, `gcloud` and `az` the kube context, GCP project or Azure subscription the command targets) plus name hints (`prod`, `production`, `prd`, `live` as a whole word between `/ _ . : -` or the ends, so `acme-prod-tfstate` matches and `acme-products-tfstate` does not; the word is ignored when the word just before it is `non`, `not`, `no` or `pre`, or the word just after it is `like`, `test` or `sandbox`, so `non-prod`, `non_prod`, `pre-prod`, `not-live` and `prod-like` are not hints while `my-prod`, `nonprod-live` and `non-prod/us-east-1/prod` are; only the adjacent words count, and glued forms such as `nonprod` and `preprod` were never whole words). Name hints are checked on the path, workspace, AWS profile, the backend URL, the backend's `bucket`, `key`, `workspace_key_prefix`, `dynamodb_table` and `address` values, and the name of a `-backend-config` file. The backend values come from `.terraform/terraform.tfstate`, or, when an init in the same command line passes `-backend-config` files or `key=value` pairs, from those (the two paths use the same rules). The values are read whether or not the backend type is known (a directory may have no `backend` block and no `.terraform` yet). A `-backend-config` file is read as Terraform reads it, as HCL, or as JSON when its name ends in `.json`; a file that does not parse (an unquoted `bucket=x` included), a computed value, a file that cannot be read, and a file an earlier step of the same command writes make the backend unknown. A computed value in the declared block stays unknown when `-backend-config` sets other keys. Local state named with `-state`, `-state-out` or `-backup`, or by a `local` backend's `path`, brings the tier of its directory. The declared backend is read from `.tf` and `.tf.json` files, override files last, with quoted or unquoted labels; `cloud` and `remote` workspace names are signals too. A backend value that is computed (a variable or local, which OpenTofu allows, a function call, a template) or a `.tf.json` backend that does not parse makes the backend unknown, and an unknown backend is judged as protected. The `profile` and `assume_role` (and `assume_role_with_web_identity`) `role_arn` of every `aws` provider block, aliases included, are signals as well (matched against `aws_profiles`, `aws_accounts` and name hints). A value that is `var.NAME` gives every value the variable can have: `-var`, `-var-file`, `TF_VAR_NAME`, `terraform.tfvars`, `*.auto.tfvars` and its default; a variable with no value found, an unreadable `-var-file` or any other computed value makes the target unknown, and judged as protected. For Terragrunt, the unit's `remote_state` values are name hints (the literal parts of a value built with functions count), a local `terraform.source`, `--source` or `TG_SOURCE` brings the tier of the directory it names, and `--config` (`TG_CONFIG`) judges the call in both the config's directory and the working directory. The AWS profile is `AWS_PROFILE`, else `AWS_DEFAULT_PROFILE`; helm's context is `--kube-context`, else `HELM_KUBECONTEXT`. A `kubectl config use-context`, `gcloud config set project` or `az account set` earlier in the same command is the target of the later calls that name none. A workspace selected earlier in the same command with a name that cannot be resolved is unknown, and judged as protected. A `..` is resolved where the path so far really leads, after symlinks, as the kernel resolves it (`-chdir=m/..` with `m` a link into `prod` is `prod`); a `cd` through such a path goes there with `-P` and is unknown without it, since the shell's logical and physical answers differ. Repository configs are found from the directory's real path, so a directory reached through a link from outside the repository still gets the repository's config. A directory reached through a symlink is matched as written and as it resolves, and a target no environment matches gets the strict or `default_tier` rule. A command whose directory is under a repository config the session's config did not read (a `cd` or `-chdir` into another repository) is also judged by that repository's config, and the stricter tier wins. When signals disagree, the most protected tier wins. If nothing matches, the tier is protected in strict mode (the default) or `default_tier` otherwise. The directory a shell command is judged in starts from the agent's hook event: for Claude Code the event's `cwd`, which is the shell's current directory at the time of the call (it follows an earlier `cd`); for Codex `tool_input.workdir`, `working_directory` or `cwd` when the event carries one, relative values resolved against the event's `cwd`. A `cd` inside the command moves it from there, and the decision log records the directory used as the action's `dir`. A shell started with `BASH_ENV` or `ENV` set, `ZDOTDIR` (zsh) or `--rcfile` runs that start-up file first, and the analyzer reads it there too; one it cannot name or read exactly is unresolved. `hash -p PATH NAME` makes a later `NAME` run `PATH`, and a zsh glob qualifier that runs code (`*(e:…:)`, `*(+f)`) is unresolved. **When the host does not report the command's directory** (Codex 0.165.0 sends no workdir, so the event's `cwd` is only the session root; `docs/hosts.md`), the command could run anywhere under that root and, with `unknown_dir: most_protected` (the default), its tier is the most protected one it could have there: the root itself with its signals, every environment whose path globs could match a directory under the root, every environment matched by workspace, backend, AWS profile or account (a directory under the root could carry any of those), and the strict or `default_tier` rule for a directory under the root that matches no environment (skipped when one environment's `/**` glob covers the whole subtree). Name hints on subdirectory names are not considered. The action's `matched` starts with `command directory not reported by codex; judged at the most protected tier under <root> (<env>, tier <tier>)`, so the decision log and `applygate explain --dir-unknown` show why. A `cd`, `pushd` or `-chdir` inside the command establishes the directory for that invocation. **When the analysis loses the directory** (a `cd` or `-chdir` to a computed path, a bare `cd NAME` after the command sets `CDPATH` or `shopt -s cdable_vars` (a `CDPATH` from your own environment is followed as bash does), a `cd` to a tilde form other than `~` and `~/…` (`~-`, `~+`, `~user`), a script written earlier in the same command, a `command_not_found_handle` (which runs at any later point), a `cd` into a directory an earlier step links, moves or extracts into, a login `su -`, a `popd` past the stack), or **stops** (a parse error, the statement budget, the work limit), the action is judged the same way under the repository root (the directory of the outermost `.applygate.yaml`, else the event's directory), whatever `unknown_dir` says, and `matched` says why. With `unknown_dir: session_root` (user config only) the command is judged at the root as if it ran there, and `matched` says so.
5. Preflight: backend changed since init, stale or archived state (and, when `preflight.live_state` is on in the user config, a read-only state pull that compares lineage and serial), and (for applies and destroys) lock-file and source drift since HEAD.
6. Plan gate for `apply <planfile>`: planfile workspace vs. selected workspace, then the `show -json` rules. When the command's directory is unknown (step 4) and a relative planfile is not in the reported directory, applygate first searches for it under the root (bounded: `.git` and `.terraform` skipped, 8 levels, 20,000 directories): one copy identifies the command directory, which is then judged as known and where `show -json` runs; several are a critical `plan-ambiguous` finding and nothing is read; none keeps `plan-missing`. A plan file kept in another Terraform directory was made against that directory's state, so that directory's tier joins the command's (`terraform apply ../prod/tfplan` from `dev` is a protected-tier action); a plan file kept outside one (`/tmp`) says nothing about where it was made. A search cut short by its limits, the depth limit included, is `plan-ambiguous` too. When the two workspaces differ, the action is judged by the more protected of the two tiers (a `prod` plan applied from `staging` is a protected-tier action, and the log records that tier), so the critical workspace-mismatch finding blocks whichever side is protected. A planfile that an earlier step of the same command writes, or names as an argument of a program applygate does not model (`aws s3 cp`, `scp`, `rclone`, `7z x`, a script), is a critical `plan-unverifiable` finding, since the plan on disk is not the one that would be applied. A plan that deletes or replaces any resource is reclassified as **destroy**: a replace destroys the old instance, so it is judged like a delete. Before `show -json` runs, the providers it would start are checked against `.terraform.lock.hcl` as git HEAD has it, and with Terragrunt the plan is shown with `terraform` in the `.terragrunt-cache` directory that holds it, never with `terragrunt show` ([limits.md](limits.md)). The engine is `plan_gate.engines` when set, else the name on `PATH`; under a managed install it must be owned and writable by root only, or the plan is unverifiable ([managed.md](managed.md)).
7. Verdict = max(class × tier, finding severity × tier) across all actions. If the host cannot ask, ask becomes block. Observe mode logs the verdict and returns allow.
8. MCP calls. A call to a known infrastructure MCP tool is first translated into the command it is equivalent to and judged by steps 2 to 7 as that command; the table and its limits are in [mcp.md](mcp.md). A shell tool of a server the table does not know is judged as a shell command, and a call that names a guard file is judged as a write to it. Other MCP calls are logged and allowed, or go to the model judge (step 10) when it is on.
9. One-time approvals (`approvals`, off by default, user config only). On one machine an agent can reach any terminal the person can, so no approval channel is out of its reach without an operating-system check, which applygate does not have yet. Until then an ask on a host that cannot prompt stays a block. When the user config turns approvals on, the hook records a request for an ask enforced as a block, and its message names an ID. A person who runs `applygate approve ID` at a terminal and types the environment name (the tier when the environment has no name) allows the agent's next identical call once, within 15 minutes; a request expires after an hour. The approval is bound to the agent, session, tool, kind of call, working directory and whether the host reported it, command, file paths, the full content of a write and the full arguments of an MCP call, and, for every action, its class, engine, command, directory, environment, tier, workspace, backend, AWS profile, kube context, GCP project, Azure subscription and plan SHA-256, so a changed command, file content, directory, environment or plan is judged afresh. A policy block can never be approved. An agent that runs `applygate approve`, including through `script`, `expect` or code in another language, is blocked as guard tampering in every tier, and the store (`approvals.json` next to the decision log) is a guard path.
10. Model judge (`judge`, off by default, user config only; [judge.md](judge.md)). After step 7, a call whose verdict is allow and in which no action was recognized goes to a language model when it passes the judge's filter (a command outside the local-only programs, any file write, an MCP call the table does not cover). The verdict becomes the stricter of the two; the model's escalation is an action of class `model-judge`, and step 9 applies to it, including to a block it gives. An error, a timeout or an allow leaves the decision unchanged.

`init -reconfigure` is state surgery only when it is bare or migrates state: with `-backend-config` (resolved files or `key=value` pairs) and without `-migrate-state`/`-force-copy` it is read-only, because it only re-points the working directory. Later commands in the same command line are then judged against the backend the config describes, and the config file's name is a name hint (`production.backend` → protected). This deviates from the original plan, which lists `init -reconfigure` as state surgery; the open-source corpus trial found it used routinely to switch environments ([oss-corpus-trial.md](oss-corpus-trial.md)).
