# Limits

applygate reduces the chance that a mistaken or manipulated agent damages infrastructure. It cannot guarantee that it won't. Use it together with plan-only credentials and an isolated runner.

## What it cannot see

- **Paths around the hook.** If the agent can reach cloud credentials and run code by any route the hook does not inspect, applygate does not see it. Examples: an MCP server with its own credentials, a tool the matcher does not cover, or a process started earlier in the background.
- **MCP tools.** A call to a known infrastructure MCP tool (AWS, HCP Terraform, Kubernetes, Helm, gcloud, az and shell-command servers) is judged as the command it is equivalent to; every other MCP call is logged with its arguments (redacted, capped at 4 KB; `applygate report` counts them per server) and allowed. The table of known tools was written from each server's source code and not tested against the running servers; what it covers and what it does not (Pulumi, the Lambda tool server, SQL, effects that live in HCP Terraform, kube-context retargeting) is in [mcp.md](mcp.md). Claude Code sends MCP calls only to hooks whose matcher covers them; `hook install` and the plugin write the matcher `*`, and `applygate doctor` warns about a narrower one. A server that runs commands in its own working directory leaves the command's directory unknown, so such calls are judged at the most protected tier under the session root.
- **Calls the rules do not recognize** are allowed: other infrastructure-as-code tools, PaaS CLIs, database clients, object storage, SDK code that does not mention a known tool, unknown scripts and MCP tools. The opt-in [model judge](judge.md) sends them to a language model, which may make the verdict stricter; it is a model, so it misses some and can be fooled, and it is off by default.
- **Encoded payloads.** `base64 -d`, `base32 -d`, `gzip`/`gunzip`/`zcat`, `xxd -r -p`, `rev` and `tee` piped into a shell are decoded and the result is analyzed. Decoder output is capped (256 KB) to stop a decompression bomb. Encodings applygate does not implement, or payloads built from unresolved runtime values, still fall back to an ask.
- **Code in other languages.** `python -c`, `node -e`, here-documents piped into an interpreter and scripts with non-shell shebangs are not executed or parsed as programs. If such code mentions terraform, tofu, kubectl, aws operations or guard files, applygate treats it as dynamic (ask) or as tampering. If it mentions none of them, it passes. Mentions of an AWS SDK (`boto3`, `botocore`, `aws-sdk`, `@aws-sdk/`, `github.com/aws/aws-sdk-go`) count too, so a script that calls AWS directly asks in protected and standard tiers, including scripts that only read. SDKs for other clouds, and code that loads the SDK indirectly (a helper module in another file), are not recognised.
  - **File-only Python and Node bodies are allowed.** Coding agents edit `.tf` and `.hcl` files with small `python3 - <<'EOF'` scripts whose text mentions `terraform` (a regex over `${terraform.workspace}`, an HCL block being inserted). A Python or Node body is treated as a file edit, allowed and noted in the decision log (`python3 code mentions terraform but only reads and writes files … treated as a file edit`) only when all of the following hold. **Known in full:** a literal `-c`/`-e` argument, a quoted or fully resolved here-document, a script file on disk; text from a decoder pipe or an unresolved variable never qualifies, and the interpreter's other arguments must resolve and name no guard or state file. **Names no sensitive file anywhere in its text**, strings and comments included: no state file (`.tfstate`, `.terraform/`, `.terraform.lock.hcl`), guard or hook config (`.applygate.yaml`, `.claude/settings*`, `managed-settings*`, `.codex/`, `.cursor/`, the config's `protected_paths` and `log_path`), credential store (`.aws/credentials`, `.aws/config`, `~/.aws`, `.terraformrc`, `.terraform.d/credentials.tfrc.json`, `.netrc`, `.pypirc`, `.npmrc`), shell start-up file (`.bashrc`, `.profile`, `.zshrc`, `.envrc`, …), `.ssh`, `.kube`, `.docker`, `.git/hooks`, `authorized_keys`, `crontab`/`cron.d`, `sitecustomize` or `.pth`. The directory names need a path boundary, so `provider.aws` or `module.aws` in HCL text and the word `applygate` in a comment are not matches. This rule means an edit that inserts an HCL block containing `terraform.tfstate` as text asks (trial edit B45 in the pack is a documented ask for that reason). **Imports only text and file modules** (`re`, `sys`, `os`, `json`, `glob`, `io`, `yaml`, `hcl2`, `csv`, … for Python; `fs`, `path`, `os`, `util`, … for Node, with or without `node:`), found anywhere in the code (after `if …:` and `try:` too), so a local helper module or a network, cloud-SDK, decoder, `pathlib` (its `/` joins cannot be followed), `fileinput`, `tempfile` or `asyncio` module keeps it opaque, as do `import os as …`, `from os import …` and importing a file function by name (`from io import FileIO`). **Nothing in its code names a way to run, load or reach into anything, called or passed by reference.** Python code is first split from its string literals and comments, so these checks see identifiers only: `subprocess` (as a substring, so `create_subprocess_shell` counts), `os.system`, `os.exec*`, `os.popen`, `os.spawn*`, `os.fork*`, `os.chdir`, `os.environ`, `os.fdopen`, `pty`, `shutil`, `importlib`, `__import__`, `eval`, `exec`, `compile`, `getattr`, `setattr`, `help`, `breakpoint`, `ctypes`, `pickle`, `sys.modules`, `sys.call_tracing`, `sys._getframe` and frame attributes, `operator.attrgetter`/`methodcaller`/`call`, `string.Formatter`, `argparse.FileType`, `__call__` and every other double-underscore or private (`._x`) attribute, `yaml.load`/`Loader`, and `os`, `io` or `sys` reached through another module (`glob.os`, `yaml.io.open`); a writing file function (`open`, `io.FileIO`, `os.rename`, `os.replace`, `os.symlink`, `os.remove`, …) used without a call (`f=open`, `map(os.system, …)`, `[open][0]`, `functools.partial(os.replace, …)`) is "passed by reference" and keeps the ask. Node bodies are checked as whole text (their regular-expression literals make a scanner ambiguous), which is more conservative: `child_process`, `execSync`, `spawn`, `exec`, `fork`, `.call`/`.apply`/`.bind`, `eval`, `new Function`, `vm`, computed `require(…)`/`import(…)`, `fetch`, `process.binding`, `process.chdir`, writes to `process.env`, `globalThis`, `constructor`, a member reached with a string (`fs['writeFileSync']`), and a writing `fs` function used without a call (`const w = fs.writeFileSync`; the destructuring idiom `const {writeFileSync} = require('fs')` is fine unless it aliases a name). **Builds no text at run time** (`\x..`/`\u....` escapes, `chr()`, `fromhex`, `[::-1]`, `base64`, `atob`, `fromCharCode`; identifiers are NFKC-folded first, as Python does). **Every write target passes a positive rule.** Every file it writes, creates, renames, links, copies or removes (`open` with a writing or unknown mode, `io.FileIO`, `os.open`, `os.remove`/`rename`/`replace`/`symlink`/`link`/`mkdir`/`chmod`/…, `fs.writeFileSync`/`renameSync`/`symlinkSync`/`cpSync`/…) must be named by a complete string literal, or a name bound exactly once to one and never bound again (not by a `for` loop or comprehension, a `with`/`except`/`import … as` alias, a `def`, `lambda`, `function`, arrow or `catch` parameter, a `def` or `class` name, a `match`/`case` capture, tuple or object destructuring, an ES `import`, `global`/`nonlocal` or a walrus); that path, resolved against the working directory, must stay under it (no `..` escape, no absolute path elsewhere; with the directory unknown only a relative path without `..` is judged, on its own text), contain no hidden segment (`.github/`, `.git/`, `.envrc`, `.tflint.hcl`, guard directories), not be a tool manifest (`package.json`, `pyproject.toml`, `Pipfile`, `Cargo.toml`, `docker-compose.yml`, `buildspec.yml`, `atlantis.yaml`, …) and end in a repository-configuration extension: `.tf`, `.tfvars`, `.hcl`, `.json`, `.yaml`/`.yml`, `.md`, `.txt`, `.toml`, `.tftpl`, `.tpl`, `.csv`, `.rst` (so `.tf.json` and `.auto.tfvars.json` too). `mkdir`/`rmdir` and friends need no extension. A target it cannot resolve (concatenation, f-string or template literal with substitutions, `%` or `.format`, `.join`, `os.path.join`, a reassigned or rebound name, a keyword argument) keeps the body opaque: the check fails closed. Reads of unresolved paths are fine, and reads are not held to the positive rule (a read of a state or credential file is caught by the text rule). Any other body that mentions a tool keeps today's ask or block, and the reason names the construct (`uses subprocess`, `uses getattr()`, `passes open by reference`, `open() writes to a path it builds at run time`, `names the state file terraform.tfstate`, `writes run.sh (not a repository configuration file)`, `writes ../x.tf outside the working directory`). What the rule does not judge: the content written. A `.tf` file gaining a `local-exec` provisioner or a `terragrunt.hcl` gaining a `before_hook` is a file edit here exactly as `sed -i` or `cat >` on the same file is; those run only through a later `apply` or `terragrunt` command, which is judged on its own. Perl, Ruby, PHP and PowerShell bodies are never treated as file edits. The check reads text, not a program, so a body with no tool mention at all is not examined, as before.
- **Runtime values.** Environment variables applygate cannot see, `read` from stdin, and command substitutions other than echo/printf/cat/base64/xxd/rev/which/dirname are unresolved. So are words the shell would expand against the disk or the locale (an unquoted glob, zsh's `=name`, `$'\u…'`), the variables assigned by `read`, `printf -v`, `mapfile` and `getopts`, and every variable after `declare -n`. In a command position they cause an ask. As plain arguments to non-infrastructure programs they do not.
- **Files written earlier in the same command.** A script, sourced file, `$(cat f)` input or makefile that an earlier step writes is unresolved, not read as it is on disk. The steps followed are redirects, `tee`, `cp`/`mv`/`ln`/`install`/`rsync`, `dd of=`, `curl -o`/`wget -O`, `sed -i`/`perl -i`, `tar`/`unzip` extraction and the git commands that rewrite the tree. A file written another way (an interpreter's `open()`, a program the analyzer does not know) is read as it is on disk. A `cd` into a directory that an earlier step links, moves, copies or extracts into makes the directory unknown, which is judged at the most protected tier under the repository root. A `cd` after `mkdir` keeps the path.
- **A directory the analysis loses.** `cd` or `-chdir` to a computed path, a `popd` past the stack, a login shell (`su -`), and a parse error, statement budget or work limit are judged at the most protected tier under the repository root (the directory of the outermost `.applygate.yaml`, else the session directory). A shell runs the lines before a syntax error, so those are analyzed too.
- **Credential and secrets runners.** `aws-vault exec`, `aws-okta exec`, `gds aws`, `saml2aws exec`, `aws-sso exec`, `envchain`, `doppler run`, `op run`, `chamber exec`, `infisical run` and `dotenvx run` are unwrapped and the wrapped command is analyzed, with or without `--`; the command-line string of `doppler run --command`, `infisical run --command` and `sops exec-env`/`exec-file` is analyzed as shell. So are the development-environment runners `direnv exec`, `mise`/`rtx exec`, `asdf exec`, `devbox run`, `nix develop|shell -c` and `nix-shell --run`, and any program listed under `wrappers:` in the config. For any other program, a backstop analyzes the arguments from a standalone `terraform`, `tofu` or `terragrunt` onward, and the value of a `--run`/`--command`/`-c`/`--cmd`/`--exec`/`-x` flag that starts with one of them. Still not seen: an unknown runner wrapping another tool (`aws`, `kubectl`) unless it is listed in `wrappers:`, and a command passed as one quoted argument without such a flag (`foo run "terraform destroy"`), which is left alone because quoted strings are where text mentions live ([backstop.md](../review/oss-corpus/backstop.md)).
- **Aliases and functions from the user's shell profile.** Only aliases defined in the same command or in config (`aliases:`, default `tf: terraform`) are expanded. They are expanded wherever the name appears, as if `expand_aliases` were on, and also on the line that defines them, which a shell does not do.
- **Remote and container contexts.** `ssh host '…'` is analyzed with an unknown directory, which is protected in strict mode. `docker run … hashicorp/terraform …` is unwrapped only when the image name contains terraform, tofu or terragrunt.
- **`make`** variables are expanded only when the Makefile defines them literally. `include` is followed for literal file names; pattern rules and functions are not. `MAKEFILES`, `MAKEFLAGS` and `--eval` cannot be analyzed and are asked about in protected tiers.
- **Other shells.** `fish`, `csh`, `tcsh`, `nu`, `elvish` and `xonsh` code is read with the bash parser. Text it cannot parse is a problem (an ask in protected tiers); text it parses differently from that shell is analyzed as bash.
- **Backend blocks** are read with a small parser that only understands literal string attributes. Partial configuration (`-backend-config`) is visible only through the `.terraform` cache.

## Plan gate

- applygate never runs `plan`. For `apply <planfile>` it runs `terraform show -json <planfile>` (`tofu` for OpenTofu). show is read-only, but it starts the provider plugins in `.terraform/providers` (or `TF_DATA_DIR`) to load their schemas, and the agent can write that directory. So first, every provider there must match an `h1:` hash in `.terraform.lock.hcl` as git HEAD has it. A lock file edited in the working tree is not trusted, a replaced provider does not match, and a directory without a committed lock file cannot have its plan read. show runs without the user's CLI configuration (`TF_CLI_CONFIG_FILE=/dev/null`), so `dev_overrides` cannot point it at other binaries. With Terragrunt the plan is shown with `terraform` in the one `.terragrunt-cache` directory that holds it (`TG_TF_PATH` or `TERRAGRUNT_TFPATH` from the hook's own environment names another binary). `terragrunt show` is never run, because it evaluates `run_cmd()` and hooks. If any of this fails, the plan counts as unreadable: a critical finding, so protected tiers block. Set `plan_gate.run_show: false` to skip running show. Applying saved plans in protected tiers is then blocked.
- **What the provider check does not cover:** the `terraform` binary on the hook's `PATH`, and a provider whose lock-file entry was committed with the replaced binary's hash. The opt-in `preflight.live_state` runs `terraform state pull`, which reads the user's CLI configuration for credentials and is not checked the same way.
- **Values known only after apply.** A watched attribute that the plan does not know, such as a security group CIDR taken from a VPC created in the same plan, is a high `unknown-watched` finding: an ask in a protected tier. A first apply of a network stack in a protected tier is therefore usually asked about.
- The rules are AWS-first. GCP and Azure resources are counted for destroy and replace, but their stateful types and protections are not known. `protected_resources` in config covers addresses of any type.
- The `code-execution` finding reads provisioners from the plan's `configuration` block and flags them for the instances the plan creates, replaces or destroys. The plan JSON does not say whether a provisioner is a creation-time or a destroy-time one, so a destroy flags both kinds. A plan produced without configuration (hand-built JSON) reveals no provisioners. An `external` data source is flagged only when its read is deferred to apply (a `read` in `resource_changes`); one read during `terraform plan` has already run by the time the gate sees the plan. Running `terraform plan` is not judged by the plan gate; in a protected directory strict shapes asks about it when the configuration has a data source, provider or backend block that runs a program (docs/policy.md, step 3). `http` data sources and provider-side code paths are not flagged.
- The workspace check reads the workspace that Terraform 1.x and OpenTofu record in the planfile (protobuf field 13 → 3). This was verified on a Terraform 1.16.1 planfile only.

## Agents

What each host can do with the hook, as verified live, is the generated table in [hosts.md](hosts.md) (`applygate hosts` prints it). The limits that follow are the ones that shape applygate's behaviour.

- **Claude Code:** only `dontAsk` turns a hook "ask" into a block. In `bypassPermissions` Claude Code still shows the ask prompt — this was observed live on Claude Code 2.1.312 (test T3.2), but it is **not documented**, so the behavior could change. Rerun T3.2 (`review/manual_agent_tests.md`) on each new Claude Code version; if a future version silently allows an "ask" under `bypassPermissions`, restore the ask→block conversion for that mode.
- **Codex:** does not support "ask" (it fails the hook and runs the tool), so every ask becomes a block. Codex hooks need to be trusted with `/hooks` before they run.
- **One-time approvals.** Off by default. Turned on in the user config, `applygate approve ID` lets a person allow one asked call on an agent that cannot ask ([policy.md](policy.md) step 9). It is meant for a person at a terminal: the command checks that its input is a real terminal (isatty) and wants the environment name typed, and the hook blocks an agent that runs it directly, through `script` or `expect`, or from Python, Node or other code that names it. Like every guard path, the store is protected only against routes the hook inspects: code in another language that writes the file without naming it, or a process the agent started earlier, is not seen. The approval matches the call as the hook sees it; it cannot tell whether the files a script reads changed between the request and the retry.
- **Codex fails open on crashes.** Codex has no `onFailure` equivalent: a missing, killed or crashed hook lets the tool call run (observed: exit 127 and a no-status-code exit both proceed). applygate recovers panics inside its own process and blocks, so the only remaining fail-open case is the binary not starting. This cannot be fixed from inside the hook — use Codex's own sandbox (`--sandbox read-only`/`workspace-write`) and approval settings as the backstop, keep plan-only credentials, and run `applygate doctor` (it checks the hook entry exists and the binary is executable, and flags hook entries it does not recognise).
- **Launch directory (project scope).** Claude Code and Codex read *project* settings only from the directory the session is launched in, not from ancestors. A hook installed at `<repo>/.claude/settings.json` is therefore silent if the agent is started from a subdirectory such as `<repo>/envs/prod` (observed on Claude Code 2.1.312, T3.1; the Codex side follows its docs and is not tested live). `applygate init` therefore installs the hook at **user scope** (`~/.claude/settings.json`, `~/.codex/hooks.json`), where it fires from any directory of any repository; `applygate hook install` defaults to project scope and takes `--scope user`. A user-scope hook also runs in repositories that have no `.applygate.yaml`; those are judged by the user config or the defaults (enforce, strict). `applygate doctor` **fails** (exit 1) when it is run in a subdirectory of a repository whose applygate hook is project-scoped only and no user-scope hook exists for that agent, and prints the install command that fixes it; it warns when a project hook and a user hook are both installed, since the hook then runs twice. For organisations, managed settings remain the answer that neither developers nor agents can remove ([threat-model.md](threat-model.md)).
- **Codex working directory.** Codex runs each shell command in the `workdir` the model passes to its `exec_command` tool, but Codex 0.165.0 builds the PreToolUse hook input from that call as `tool_input: {"command": ...}` only, and its top-level `cwd` is the session's directory, not the command's (openai/codex at `rust-v0.165.0`: `codex-rs/core/src/tools/handlers/unified_exec/exec_command.rs`, `pre_tool_use_payload`; `codex-rs/core/src/hook_runtime.rs`, `tool_hook_cwd`; the same on `main` at the time of reading; confirmed by a captured hook input, `review/agent-trial/results/2026-10-29-codex-hook-payload/README.md`). This was observed in the agent-driven trial (`terraform-aws-vpc`, `examples/simple`): every Codex decision was resolved against the root. applygate reads `tool_input.workdir`, `working_directory` or `cwd` (relative values resolve against the hook `cwd`) whenever a Codex version sends one. **When no workdir arrives, the command's directory is unknown and applygate fails closed:** it judges the command at the most protected tier it could be in under the session root (every environment whose path globs could match a directory under the root, every environment matched by workspace, backend or AWS profile, and the strict or `default_tier` rule for an unmatched directory; name hints on subdirectory names are not considered). So a bare `terraform destroy` under a root that also holds `envs/prod/**` is a protected-tier destroy (block) even if Codex ran it in a disposable example directory, and under the default `strict: true` any root is protected. The action's `matched` line in the decision log and in `applygate explain --dir-unknown` says so: `command directory not reported by codex; judged at the most protected tier under <root> (<env>, tier <tier>)`. A `cd`, `pushd` or `-chdir` inside the command establishes the directory for that invocation (a relative one is resolved against the session root, which is the best information the host gives). For `apply <planfile>` with a relative planfile that is not in the root, applygate searches for it under the root (skipping `.git` and `.terraform`, at most 8 levels deep and 20,000 directories): exactly one copy identifies the command directory and the plan gate reads it there (`show -json` runs in that directory, with its provider schemas); several copies are a critical `plan-ambiguous` finding (block in protected tiers, ask elsewhere, which Codex enforces as a block); none keeps `plan-missing`. The user config's `unknown_dir: session_root` restores judging at the root ([config.md](config.md)); a repository config cannot loosen it. The cost of the rule is over-protection: with the default config a Codex session rooted in a repository with a protected directory cannot run a destroy or an unreviewed apply anywhere in it without a `cd` in the command or a less protected root. Tell Codex to `cd` into the directory inside the command instead of using `workdir`, launch the session from the subdirectory, or (your call) set `unknown_dir: session_root` in the user config. `apply_patch` paths are relative to the session directory in Codex too, so file edits are resolved correctly. MCP tool calls arrive with `tool_name` `mcp__<server>__<tool>` and the tool's raw arguments as `tool_input`; known infrastructure tools are judged as described in [mcp.md](mcp.md).
- **Adapters written from documentation.** The adapters for Cursor, Copilot CLI, Gemini CLI, Windsurf (Cascade), Devin, OpenCode and Cline follow each host's documentation and source as read on 2026-10-30 and 2026-10-31 ([review/host-research/2026-10-31-hook-contracts.md](../review/host-research/2026-10-31-hook-contracts.md)); none has been run inside its host. The scenario pack replays through each of them in the documented payload format (`go test ./harness`, `harness/run.py --format NAME`), which checks applygate's reading and writing of those formats, not the hosts. Where a host does not document a field, the adapter is conservative: a shell call whose command it cannot read fails per `on_error`; a write tool without a known path field has every one-line string argument checked as a path; a directory the payload does not name is unconfirmed. Hosts that do not report the command's directory (Copilot CLI, Windsurf, Devin, Cursor's `beforeShellExecution`) get the same most-protected-tier rule as Codex. Gemini CLI, Windsurf and Devin let a tool call run when the hook crashes or is missing; Cline does on a timeout, and a Cline cancel ends the whole task.
- **A hook loaded by another host.** Cursor, Copilot CLI and Devin also run hooks from `.claude/settings.json`. The Claude Code hook then receives their tool names (`Shell`, `exec`); applygate judges those shell calls like that host's own (no ask; a block is exit 2), so a cross-loaded hook does not let a shell command through as an unknown tool. Whether those hosts apply the Claude Code matcher to their own tool names is not documented, so install the host's own hook rather than relying on this.
- **When applygate fails.** Errors applygate catches (a malformed event, a repository config error, a panic) follow the user config's `on_error` and mode: with `auto`, the default, they block when the most protected tier under the repository root is protected or unknown, and allow otherwise, since a command that was not analyzed could run anywhere under it. A block is exit 2 for Claude Code and Codex; Cline gets a cancel instead, since it ignores exit codes. A decision that misses the internal 25 s deadline (for example a slow `terraform show`) cancels the in-flight work, including the `show` subprocess, and blocks in every tier whatever `on_error` says. A watchdog holds the whole run, config reading and the judge included, to 29 s: past that the hook answers with a block itself, in observe mode too, since the config may not have been read. Config files over 1 MiB are not read: a repository config that large is untrusted (protected), and a user or system config that large is an error. A brace sequence over about a million words, or a word or variable value that grows past 64 KiB through expansion, is unresolved. Failures it cannot catch (the binary missing or killed, the agent's own hook timeout) are decided by the agent: Claude Code blocks because `applygate hook install` sets `"onFailure": "block"` (Claude Code 2.1.295 or later; older versions fail open); Codex fails open (above); the other hosts are listed in [hosts.md](hosts.md). Observe mode never blocks, including on errors. A user config that cannot be read blocks in every mode, since its `on_error` and mode are what is unknown.

## Known gaps

The v0.6.0 pre-release review ([review/v0.6.0](../review/v0.6.0)) left these open, by decision or because they need a live test. The next red-team round keeps this list current.

- **Tier signals not read (round 2, R2-3):**
  - Terragrunt `dependency` and `include` blocks that point outside the unit, and a remote `terraform.source` (its module's own backend block); the unit's `remote_state`, a local source, `--source`, `TG_SOURCE`, `--config` and the working-directory options are read.
  - Provider profiles and roles set in modules, or through anything other than a literal or a bare `var.NAME`; those are unknown, so protected.
  - The backend recorded inside a binary planfile. A plan file kept in another Terraform directory brings that directory's tier, but a plan copied elsewhere carries only its workspace.
  - An S3 lifecycle rule that expires objects is not a finding, since it is often deliberate.
- **Self-protection without a managed install is best-effort** ([threat-model.md](threat-model.md#self-protection)). Red-team round 4 found ten routes past it in one pass; they are not fixed one by one, and the managed install is the documented guarantee.
- **Shapes are a table.** A program whose shape takes any arguments (`ls`, `cat`, `grep`, `terraform`, …) is there because no option of it is known to run another program. An option that does, if one exists, is not covered.
- **A trusted nested config can become the repository's** when the outer one is removed (red-team round 5, 5H6): trust binds a file's content to its path, not to its place in the chain. Until that is fixed, trust a nested config only if you accept its environments applying on their own.
- **Widening an already-public resource policy** (a bucket policy public for one prefix made public for all of it) on an update is not a finding: the exposure rule reports whether a policy is public, not how much.
- **Open from red-team round 7** ([review](../review/v0.6.0/2026-11-04-red-team-round-7.md)): the highs and mediums its fix plan lists under R7-3. The criticals are fixed; their reproductions are in `harness/pack_attack` (Y7*). The OS-level backstop (R7-2) is not built yet.
- **What strict shapes trusts.** A program found on `PATH` by name is the program it names, and so is a program git config names (an editor, a pager, gpg, a credential helper). Writing one into a `PATH` directory the user can write is blocked as tampering, but a route the hook does not see can place one there. The Homebrew prefix on Apple silicon is the user's to write.
- **The terraform provider check trusts the upstream branch.** Providers must match the lock file committed at HEAD, and that file must match the upstream branch's. A branch without an upstream relies on HEAD alone, which the agent can commit to; `git branch --unset-upstream` is still plain (R7-3). The check reads `.terraform/providers` (or `TF_DATA_DIR`), not provider `dev_overrides` in the CLI configuration, which is a guard file.
- **Shell semantics.** The command is parsed as bash. zsh's own tables (`functions`, `commands`, `path`), `hash NAME=PATH`, its hook functions, `chdir`, the `nocorrect` and `-` modifiers and a `cd` as a pipeline's last element are handled; other zsh-only syntax that bash parses differently may not be.
- **Costs of the round-7 fixes:**

A configuration file over 1 MiB, or one that does not parse, counts as one that may run programs.
  - A git network command whose repository is a word that is not a URL, an scp-like address or a configured remote asks when a directory of that name exists; `git --bare` asks.
  - On macOS `sed -i` takes the next word as the backup suffix, as BSD sed does, so `sed -i 's/a/b/' eks.tf` asks (BSD sed would read `eks.tf` as the script).
  - Input typed into a persistent shell is judged as protected: a destroy there blocks in a disposable directory too, and a terraform call that starts providers asks.
  - Installing, updating or replacing an agent CLI (`claude update`, `npm i -g @anthropic-ai/claude-code`, `brew upgrade codex`, a copy into `~/.local/share/claude`) is blocked in every tier: a person does it.
  - On the agent trial, 54 of 162 calls in a protected directory are asked about or blocked, against 51 before; staging and dev each have one more ask.
- **Costs of the round-6 fixes:**
  - Strict shapes: `make` and every `terragrunt` command but `hclfmt` and its version ask in a protected directory; so does `terraform plan`, `validate`, `console` or `show` when the providers do not match a committed lock file (a repository that does not commit `.terraform.lock.hcl` included), when the committed lock file differs from the upstream branch's, or when the configuration has a `data "external"`. A git command asks when any git config it reads has a key off the safe list (`git lfs install`'s filter is on it; another tool's filter or diff driver is not), when the repository has a hook, or after `git init`, `git clone`, an extraction or a recursive copy earlier in the same command. On the agent trial, 51 of 162 calls in a protected directory are asked about or blocked, against 47 before.
  - Claude Code's shell snapshots and session environment files, `~/.ssh/config` (and `config*` beside it), Docker CLI plugins, `~/.curlrc`, Azure CLI extensions, `~/Library/LaunchAgents`, fish, `environment.d`, systemd user units and oh-my-zsh custom files are guard paths: writing them is blocked in every tier.
  - A nested `claude --mcp-config`, `--strict-mcp-config`, `--plugin-dir` or `--agents`, `copilot --additional-mcp-config`, `gemini --extensions` and `codex -c mcp_servers.*`, `-c notify` or `-c profiles.*` are blocked in every tier.
  - After a command whose name, or an `eval` or `source` whose text, cannot be resolved, the directory is unknown, so a later destroy in a disposable directory is judged at the most protected tier under the root (`eval "$(direnv export bash)"; terraform apply` included).
  - `find -execdir` and `-okdir`, and a directory option before the command a runner starts (`pnpm -C`, `yarn --cwd`, `npm --prefix`, `mise -C`/`--cd`, `poetry -C`, `parallel --wd`, `env --chd`), make that command's directory unknown.
  - A Terraform container is judged in the host directory mounted at its `-w`; without both, its directory is unknown.
  - A saved plan read from `/dev/…` or `/proc/…`, or written earlier in the same command by anything other than `plan -out`, is judged as protected; one made by `plan -out` in another directory brings that directory's tier; one kept in a configured environment's path brings that environment's tier.
  - A local state file in a directory no environment matches gets the tier of an unknown directory (protected under strict). `workspace new -state=PATH` passes that state's tier to later commands in the directory.
  - `terragrunt run --all`, `run-all` and `*-all` are judged at the most protected unit under the directory (each `terragrunt.hcl`, up to 2,000 directories; past that, or through a symlink, the most protected tier anything there could have).
  - The agent trial's calls get the same verdicts as before in every tier.
- **Costs of the round-5 fixes:**
  - Strict shapes with exact shapes asked about the same share of the agent trial's calls in a protected directory as before (29 of 162, measured on 2026-11-03 before the round-6 and round-7 fixes). Calls they newly ask about: `man`, `less`, `npx`, `npm`, `pip`, `cargo`, `brew`, `go build` and `go test`, `docker run`, a git command in a repository with hooks or command-running config keys, a git alias to another git command, and a variable off the safe list (`PAGER=less`, `KUBECONFIG=…`).
  - Writing a skill, subagent or command into `.claude/`, any host's MCP server list, `~/.gitconfig`, `~/.aws/config`, `~/.kube/config` or another file in which a program names a command, or a program strict shapes trusts into a `PATH` directory, is blocked in every tier: a person does it.

  - A `cd` to a directory that does not exist, and that no earlier step of the command creates, leaves the directory unknown.

- **Costs of the round-4 fixes:**
  - Strict shapes asked about 18% of real agent calls in a protected directory (29 of the agent trial's 162, measured on 2026-11-03; 54 after the round-7 fixes): loops, `python3` edits, `export`, `xargs`, `timeout`, `${x:-…}`. Turn it off with `strict_shapes: false` in the user config if you accept the shell constructs it covers.

- **Costs of the round-3 fixes:**
  - A `.applygate.yaml` that is a symlink is never read (it cannot be trusted), so a repository that shares its config by a link is judged protected until the link is replaced by the file.
  - Under a managed install, loosening settings in the user config are ignored; they belong in the system config.
  - A bare `cd NAME` after the command sets `CDPATH`, or `shopt -s cdable_vars`, is judged at the most protected tier under the root.
- **Costs of the round-2 tier fixes:**
  - A `trap` handler is judged at the most protected tier under the root, since it fires after any `cd`.
  - When the host does not report the directory, a planfile search that reaches its depth limit is `plan-ambiguous`, so a deep repository can block `apply <planfile>` from Codex until the command `cd`s into the directory.
  - A `.tf` value that is computed (OpenTofu variables in a backend block) makes every command in that directory protected.
- **A repository config that turns the judge off.** A repository config may turn the judge off for its subtree. Since R2-2 a config is read only once a person has trusted it, so a cloned or planted config cannot do this unseen.
- **Unknown wrappers around other CLIs.** A program applygate does not know that runs `aws`, `kubectl` or another CLI from its arguments (a team's own runner) is not seen through unless it is listed under `wrappers:`; only standalone `terraform`, `tofu` and `terragrunt` arguments trigger the backstop.
- **Files written another way.** A file written by interpreter code (`open()` in Python) or by a program the analyzer does not model is read as it is on disk, not as unresolved. Guard files are not affected: any program that names one is tampering unless it only reads ([threat-model.md](threat-model.md)).
- **Guard files reached without naming them.** Default-deny looks at what a command names. A command that rewrites a guard file without naming it (`git checkout <branch>` to a commit with another `.applygate.yaml`, `git checkout-index -a`) is not caught by it. For repository configs, trust covers it: a rewritten config is not read. For the other guard files, only a managed install does ([managed.md](managed.md)).
- **Managed install, untested parts.** The Claude Code managed settings keys are from its docs and have not been tested live, nor has whether `claude --bare` or `CLAUDE_CODE_SIMPLE` skip managed hooks. The Codex `requirements.toml` snippet is printed, not written, and not tested live. Windows is not supported.
- **No integrity record at hook start.** The fix plan proposed recording a hash of the hook entries and user config at install and checking it on every call. It is not built: an agent that can write the files can rewrite the record too, and a hash of a whole settings file would block on every legitimate settings change. A managed install is the answer instead.
- **Plugin pin after an upgrade.** The Claude Code plugin blocks every call once the pinned binary changes, an upgrade included, until a person removes `pinned-binary` from the plugin's data directory.
- **Code in a running REPL.** Input that an MCP shell server types into a running process is judged as a shell command, whatever the process is.
- **The plan gate's own trust:** without a managed install, a `terraform` the agent puts on the hook's `PATH` by a route the hook does not see (writing one into a `PATH` directory is blocked); a lock file committed with a replaced provider's hash; and the opt-in `preflight.live_state` pull, which is not provider-checked. Under a managed install the engine must be root's alone ([managed.md](managed.md)).
- **Cursor's allow.** Under `failClosed`, applygate must print a permission for every call, so a call it does not judge gets `{"permission":"allow"}`. Whether that skips Cursor's own approval prompt is not documented and has not been tested live.
- **Untested Claude Code paths:**
  - the `*` matcher with `Monitor` and `PowerShell` calls, which is tested only with replayed events;
  - the prompt in `acceptEdits`, `plan` and `auto` modes, where an ask is enforced as a block until tested.
- **Hosts other than Claude Code and Codex** have not been run inside the host ([hosts.md](hosts.md)).
- **The model judge's accuracy** was measured before this release's filter changes and has not been measured again.
- **One-time approvals** have no operating-system presence check, which is why they are off by default.
- **Homebrew** (`Flurit/tap`) checks the archive's sha256 only, not the cosign signature; `install.sh` and the GitHub Action verify the signature ([install.md](install.md#verify-a-download)).

## Not in v1

Backup isolation checks, receipts, Pulumi rules, and plan-gate rules for GCP, Azure and Kubernetes resources (their CLI commands are classified; plans are judged with AWS rules only). Plan-hash approval (`applygate approve`) and CI mode (the GitHub Action) were pulled forward from v2 ([roadmap.md](roadmap.md)). The only network calls are the optional model judge, which sends each call it judges (redacted) to the endpoint or program the user chose ([judge.md](judge.md)); the optional STS identity check (`preflight.live_identity`); the optional state pull for lineage comparison (`preflight.live_state`); and, after a person runs `applygate telemetry on`, one anonymous usage report a day ([telemetry.md](telemetry.md)). Only the user config or the person at the terminal can enable any of them.
