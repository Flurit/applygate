# Limits

seatbelt reduces the chance that a mistaken or manipulated agent damages infrastructure. It cannot guarantee that it won't. Use it together with plan-only credentials and an isolated runner.

## What it cannot see

- **Paths around the hook.** If the agent can reach cloud credentials and run code by any route the hook does not inspect, seatbelt does not see it. Examples: an MCP server with its own credentials, a tool the matcher does not cover, or a process started earlier in the background.
- **MCP tools (spec stretch scenario S13).** A destructive call made through a Terraform or cloud MCP server arrives as an `mcp__…` tool call, not a shell command. seatbelt does not inspect MCP tool inputs in v1; such calls pass through unlogged. Restrict MCP servers with the agent's own permission rules, or give them plan-only credentials.
- **Encoded payloads.** `base64 -d`, `base32 -d`, `gzip`/`gunzip`/`zcat`, `xxd -r -p`, `rev` and `tee` piped into a shell are decoded and the result is analyzed. Decoder output is capped (256 KB) to stop a decompression bomb. Encodings seatbelt does not implement, or payloads built from unresolved runtime values, still fall back to an ask.
- **Code in other languages.** `python -c`, `node -e` and scripts with non-shell shebangs are not analyzed. If such code mentions terraform, tofu, kubectl, aws operations or guard files, seatbelt treats it as dynamic (ask) or as tampering. If it mentions none of them, it passes. Mentions of an AWS SDK (`boto3`, `botocore`, `aws-sdk`, `@aws-sdk/`, `github.com/aws/aws-sdk-go`) count too, so a script that calls AWS directly asks in protected and standard tiers, including scripts that only read. SDKs for other clouds, and code that loads the SDK indirectly (a helper module in another file), are not recognised.
- **Runtime values.** Environment variables seatbelt cannot see, files written earlier in the same command, `read` from stdin, and command substitutions other than echo/printf/cat/base64/xxd/rev/which/dirname are unresolved. In a command position they cause an ask. As plain arguments to non-infrastructure programs they do not.
- **Credential and secrets runners.** `aws-vault exec`, `aws-okta exec`, `gds aws`, `saml2aws exec`, `aws-sso exec`, `envchain`, `doppler run`, `op run`, `chamber exec` and `infisical run` are unwrapped and the wrapped command is analyzed. So are the development-environment runners `direnv exec`, `mise`/`rtx exec`, `asdf exec`, `devbox run`, `nix develop|shell -c` and `nix-shell --run`, and any program listed under `wrappers:` in the config. For any other program, a backstop analyzes the arguments from a standalone `terraform`, `tofu` or `terragrunt` onward, and the value of a `--run`/`--command`/`-c`/`--cmd`/`--exec`/`-x` flag that starts with one of them. Still not seen: an unknown runner wrapping another tool (`aws`, `kubectl`) unless it is listed in `wrappers:`, and a command passed as one quoted argument without such a flag (`foo run "terraform destroy"`), which is left alone because quoted strings are where text mentions live ([backstop.md](../review/oss-corpus/backstop.md)).
- **Aliases and functions from the user's shell profile.** Only aliases defined in the same command or in config (`aliases:`, default `tf: terraform`) are expanded.
- **Remote and container contexts.** `ssh host '…'` is analyzed with an unknown directory, which is protected in strict mode. `docker run … hashicorp/terraform …` is unwrapped only when the image name contains terraform, tofu or terragrunt.
- **`make`** variables are expanded only when the Makefile defines them literally. Includes, pattern rules and functions are not followed.
- **Backend blocks** are read with a small parser that only understands literal string attributes. Partial configuration (`-backend-config`) is visible only through the `.terraform` cache.

## Plan gate

- seatbelt never runs `plan`. For `apply <planfile>` it runs `<engine> show -json <planfile>` (read-only; it starts provider plugins to load schemas). If that fails, the plan counts as unreadable: a critical finding, so protected tiers block. Set `plan_gate.run_show: false` to skip running show. Applying saved plans in protected tiers is then blocked.
- The rules are AWS-first. GCP and Azure resources are counted for destroy and replace, but their stateful types and protections are not known. `protected_resources` in config covers addresses of any type.
- The `code-execution` finding reads provisioners and `external` data sources from the plan's `configuration` block. A plan produced without configuration (hand-built JSON) only reveals `external` data sources that appear in `resource_changes`. `http` data sources and provider-side code paths are not flagged.
- The workspace check reads the workspace that Terraform 1.x and OpenTofu record in the planfile (protobuf field 13 → 3). This was verified on a Terraform 1.16.1 planfile only.

## Agents

- **Claude Code:** only `dontAsk` turns a hook "ask" into a block. In `bypassPermissions` Claude Code still shows the ask prompt — this was observed live on Claude Code 2.1.312 (test T3.2), but it is **not documented**, so the behavior could change. Rerun T3.2 (`review/manual_agent_tests.md`) on each new Claude Code version; if a future version silently allows an "ask" under `bypassPermissions`, restore the ask→block conversion for that mode.
- **Codex:** does not support "ask" (it fails the hook and runs the tool), so every ask becomes a block. Codex hooks need to be trusted with `/hooks` before they run.
- **Codex fails open on crashes.** Codex has no `onFailure` equivalent: a missing, killed or crashed hook lets the tool call run (observed: exit 127 and a no-status-code exit both proceed). seatbelt recovers panics inside its own process and blocks, so the only remaining fail-open case is the binary not starting. This cannot be fixed from inside the hook — use Codex's own sandbox (`--sandbox read-only`/`workspace-write`) and approval settings as the backstop, keep plan-only credentials, and run `seatbelt doctor` (it checks the hook entry exists and the binary is executable, and flags hook entries it does not recognise).
- **Launch directory (project scope).** Claude Code and Codex read *project* settings only from the directory the session is launched in, not from ancestors. A hook installed at `<repo>/.claude/settings.json` is therefore silent if the agent is started from a subdirectory such as `<repo>/envs/prod`. `seatbelt doctor` warns when a project-scope seatbelt hook lives in an ancestor of the current directory. Launch the agent from the directory holding the hook, or install at user scope (`hook install --scope user`).
- Hook crashes and agent-side timeouts: see the README section "What happens when seatbelt fails".

## Not in v1

Backup isolation checks, plan-hash approval, CI mode, receipts, and GCP/Azure/Kubernetes/Pulumi rules. The only network calls are the optional STS identity check (`preflight.live_identity`) and the optional state pull for lineage comparison (`preflight.live_state`); only the user config can enable either.
