## v0.6.2 (2026-11-16)

The GitHub Action can write the plan check's verdict on the pull request, and it installs the release it is tagged at. No rule, verdict, tier or default changed: the hook decides every call and `plan-check` judges every plan as v0.6.1 does, and the scenario pack gives the same results. Nothing needs doing when upgrading from v0.6.1, except for the Claude Code plugin's pinned binary ([docs/upgrading.md](docs/upgrading.md)).

- **The Action can write its verdict on the pull request.** With `comment: true` (off by default) the plan check's verdict, the tier and environment it was judged in, and the reasons appear as a comment on the pull request, with the destroyed or replaced stateful resources first and long lists in a collapsed block. Each plan a job judges has one comment, updated in place on later runs, so a fixed plan turns its block into an allow; two workflows, jobs or matrix legs that judge the same plan each get their own. A run does not replace the comment of a later run, two steps that share a comment leave the more severe verdict, and an error of the check (including one before `plan-check` runs, or a failed install) replaces a comment that said allow. The job needs `permissions: pull-requests: write`; when the run is not for a pull request, or the token cannot comment (a pull request from a fork, a missing permission), the step says so and the job goes on. The verdict, the outputs and the exit code do not change: `plan-check` runs once and, with the new `--comment-file`, writes the comment beside its usual output. Text from the plan is written only inside code spans and never passes through a shell command ([docs/ci.md](docs/ci.md#a-comment-on-the-pull-request)).
- **The Action installs the release it is tagged at.** A workflow that says `uses: Flurit/applygate@vX.Y.Z` reads `action.yml` from that tag, and the default of its `version` input was bumped only after each release, so the Action at v0.6.0 installed v0.5.0 and the Action at v0.6.1 installs v0.6.0 (for v0.6.1 the two judge a plan the same way; set `version` to choose). From this release on, the default is set in the commit the tag is made on: a test fails while it differs from the newest changelog section, and the release workflow refuses a tag whose `action.yml` names another version. Published tags are not moved, so v0.6.0 and v0.6.1 stay as they are.
- **`scripts/ci-plan-check.sh` exits 2 for every error.** A working directory that does not exist and an unset `PLAN` exited 1, the code for a verdict that does not pass `fail-on`; they exit 2 now, as the script's header says an error does. The Action fails the job either way.
- **A page on where applygate fits.** [docs/where-it-fits.md](docs/where-it-fits.md) says which step each guard sees (the agent's shell, the pull request, the pipeline, the cloud), what the hook, the plan check and the credential audit add next to pipelines, approvals, plan-only credentials, Sentinel, OPA and Terraform policy, and who does not need the hook. Documentation only.

## v0.6.1 (2026-11-15)

A new command, `applygate scan`, and documentation. No rule, verdict, tier or default changed: the hook decides every call as v0.6.0 does, and the scenario pack gives the same results. Nothing needs doing when upgrading from v0.6.0, except for the Claude Code plugin's pinned binary ([docs/upgrading.md](docs/upgrading.md)).

- **`applygate scan`: what applygate would have decided on your agents' past calls.** It reads the sessions Claude Code and Codex already recorded on the machine, passes every tool call through the hook's own code with today's rules and config, and reports the infrastructure commands it would block or ask about, the changes to guard files, the share of other shell commands it would ask about and why, and a line per repository. No hook or config is needed. Nothing is run, written or sent: saved plans, the model judge and the live cloud checks are not asked, and printed commands are redacted as in the decision log. Verdicts use today's files, so a script or directory that changed since is judged as it is now; calls in a directory that no longer exists are counted and left out ([docs/scan.md](docs/scan.md)).
- **`applygate scan` opens with what your agents can reach.** The report starts with the boundary checks of `doctor --boundary` and the assurance level, then says how many commands that change infrastructure the agents issued, and only then what applygate would have decided. By default it makes the checks that read this machine and contacts nothing; `applygate scan --boundary` adds the credential audit, which asks AWS, Google Cloud, Azure and the clusters, read-only, whether the credentials here can change production without a person. When none of the audited credentials can, the report says you do not need the hook to protect production and points to the plan check in the pipeline.
- **The boundary report names every audited credential and says why one was not checked.** `doctor --boundary` and `scan --boundary` listed only the credentials that failed or could not be verified, so a level could rest on credentials the report never named; each audited credential now has its own line. The scan report tells a credential that could not be checked (an expired sign-in, a permission the audit needs: sign in or grant it, then run it again) from one that can make destructive changes in an environment no config names (name your environments). Both came out of the first runs of the audit against real AWS and Google Cloud accounts. `docs/credentials.md` now says what to grant when AWS refuses the simulator call.
- **`applygate scan --share`: counts only.** A summary with no command, path, repository, account or program name, for telling someone else how often applygate would get in your way. Reasons for asks are put in a fixed set of kinds instead of being quoted. applygate sends it nowhere.
- **README rewritten for a quick scan:** what it does, who it is for and what it is not come first, and terms are defined before they are used. The upgrade notes moved to [docs/upgrading.md](docs/upgrading.md) and the full command list to [docs/commands.md](docs/commands.md).

## v0.6.0 (2026-11-11)

A security release. It went through a pre-release review and eleven red-team rounds; the reports are in [review/v0.6.0](review/v0.6.0) and the known gaps in [docs/limits.md](docs/limits.md). Many fixes change a verdict or a default; the upgrade steps are in [docs/upgrading.md](docs/upgrading.md).

### Breaking changes

- **Reinstall the hooks.** The Claude Code matcher is now `*`, so every tool reaches the hook; `doctor` warns about an older one. After reinstalling the Codex hook, run `/hooks` in Codex to trust it again.
- **Repository configs must be trusted.** A `.applygate.yaml` is read only when a person approved its exact content with `applygate trust`. Until then it is not read and every directory is protected. `init` trusts the config it writes, and `doctor` lists untrusted ones.
- **Repository configs can only add protection.** Observe mode, `strict: false`, a looser `default_tier`, `name_hints` or `on_error`, `aliases` and the other loosening settings in [docs/config.md](docs/config.md) work only in the user config; in a repository config they are ignored, and `doctor` says so. A nested `.applygate.yaml` adds to the repository's and no longer replaces it. `init` starts the observe-mode trial in the user config, and `suggest` no longer proposes a mode.
- **One-time approvals are off by default.** Only the user config turns them on (`approvals: true`).
- **`applygate apply` has no `--yes` and no `--plan-json`.** An ask outside a terminal is refused. In CI, gate with `applygate plan-check` or the Action and run the engine yourself.
- **The `seatbelt` compatibility binary is gone.** A hook entry that still calls it fails; `doctor` flags one.
- **`install.sh` requires cosign** to verify the release signature; `APPLYGATE_VERIFY_SIGNATURE=auto` installs without it.
- **Building from source needs Go 1.26.11.**

### The promise and the boundary

- **README promise restated.** applygate is a pre-execution reviewer that allows only recognized commands in protected tiers, not a guarantee that a command is never allowed; the guarantee comes from the boundary.
- **`applygate doctor --boundary [--require L1|L2|L3]`** reports an assurance level from L0 to L3: a managed exclusive install, audited credentials, then a host sandbox with an attested CI apply and state guards. `boundary.require` and `boundary.attest` are user or system config only ([docs/boundary.md](docs/boundary.md)).
- **`applygate doctor --creds`** asks AWS, Google Cloud, Azure and each kube context whether the credentials the agent's environment can use may make destructive changes, and fails for production ones that can ([docs/credentials.md](docs/credentials.md)).
- **Managed install.** `sudo applygate install --managed` installs a root-owned binary, a system config that wins over the user config, and the hook in Claude Code's managed settings with bypass mode off; `--exclusive` turns other hooks off. It prints a snippet for Codex's `requirements.toml`. Under it the user config may only tighten, its `judge` section is ignored, and the plan gate runs only a root-owned engine or one named in `plan_gate.engines`. The hosts' managed keys are from their docs and not tested live. macOS and Linux only; `uninstall --managed [--purge]` removes it. Without one, self-protection is best-effort ([docs/managed.md](docs/managed.md)).

### Stricter in protected environments

- **Strict shapes are on.** In a protected environment a shell command is asked about unless it is a plain list or pipeline of known programs, each called with listed subcommands and options that run no other program. Asked about now: a loop, `bash -c`, `python3 -c`, `export`, `xargs`, `npx`, `make`, `terragrunt`, a pager or editor variable, `git push`, git with `-c` or in a repository with hooks, an unlisted option. `strict_shapes: false` in the user config turns it off.
- **Unknown means protected.** A command that is not plain and can run code the analysis does not follow (`python3`, `perl`, `awk`, a nested agent), or whose directory cannot be followed (`cd $X`, `-chdir=$x`), is also judged at the most protected tier under the repository root, so it asks from a dev directory next to a production one. A target that cannot be resolved (`TF_WORKSPACE=$X`, a computed backend) is protected, and a command that runs a file it wrote, or has a glob in its program name, is asked about. `applygate explain` shows what made a value unknown.
- **Terraform calls that may start providers** are plain only when the configuration parses, its modules are local or installed, and its providers are on a closed list and locked by a lock file the upstream branch holds.
- **State files by rule.** A program not known to only read that names a state file (overwrite, remove, move, extract, `plan -out=terraform.tfstate`, an `aws s3` write to a `backends:` bucket) is state surgery in that file's directory.
- **Network requests with a body are writes.** `curl`, `wget`, `http`/`xh` and `gh api` calls to another host that send anything but GET, HEAD or OPTIONS are cloud writes; with DELETE, deletes.
- **`helm`, `az` and `gcloud` are classified by verb:** `helm uninstall` and `delete` or `purge` verbs are destructive, `list`, `show`, `describe`, `get` and `status` read, anything else writes. Before, they were allowed in every tier.
- **Kubernetes contexts, GCP projects and Azure subscriptions pick the environment.** New matchers `kube_contexts`, `gcp_projects` and `azure_subscriptions` match the command line (`--context`, `--project`, `--subscription`), else the CLI's local configuration. Before, only the directory decided.
- **Errors fail closed.** An internal error under `on_error: auto` blocks when the repository has a protected environment. A panic never allows where a protected tier is in reach, whatever `on_error` says. The hook blocks when it passes its 29-second budget, and does not read a config file over 1 MiB.

### Self-protection

- **Default-deny near guard files.** A shell command that names a guard file, or a directory that holds one, is tampering unless the program only reads. Paths are compared after resolving symlinks and case, and code in another language that names one (`python3 -c`, `node -e`) counts.
- **More guard files:** Claude Code skills, subagents and plugins, every host's MCP server list, shell start-up files, `~/.ssh/config`, the config files in which git, aws, kubectl, gh or docker name a command, and the agent CLIs' install locations.
- **Switching the guard off through an agent CLI is tampering:** `claude --bare` or `--settings`, `codex --disable hooks`, `claude mcp add`, installing or updating an agent CLI, and `applygate hook install` or `applygate apply` run by an agent.
- **Hook files are guarded where the host loads them:** in a repository whose config is not trusted, at the git root of a repository with no `.applygate.yaml`, and in the directory a Claude Code, Gemini CLI or Devin session was started in. Removing, moving, copying or extracting into a directory there that holds hook settings is blocked.
- **Git commands that rewrite the work tree ask.** `git checkout BRANCH`, `pull`, `merge`, `rebase`, `stash`, `reset --hard`, `clean` and the like ask in a repository or session directory that holds hook settings, in every tier; hosts that cannot ask block. Restoring a guard file by name (`git checkout -- .claude/settings.json`) is blocked, and a rewritten `.applygate.yaml` is not read until it is trusted again.
- **Removing a directory counts only what its loss can weaken.** `rm -rf .terraform`, `.github` or `.vscode` at a repository root is no longer tampering when nothing under it can weaken the guard; `rm -rf .git` asks in a protected tier.

### Plan gate

- **A committed `.terraform.lock.hcl` is needed** wherever `.terraform/providers` holds providers. The providers are checked against it before `terraform show` runs; without one, a saved plan in a protected tier is blocked as unreadable. `terragrunt show` is never run.
- **Replacing a resource is a destroy:** it blocks in protected tiers and asks in standard ones.
- **A plan written or downloaded earlier in the same command is unverifiable:** `terraform plan -destroy -out=tfplan && terraform apply tfplan` is no longer judged on the old file.
- **A watched attribute known only after apply** (an ingress CIDR, `deletion_protection`) is a high finding, so a first apply of a network stack in a protected tier usually asks.
- **More exposure rules,** among them public resource policies, wildcard actions and principals, and any-principal trust policies.
- **`protected_resources` ignore `count` and `for_each` keys,** and a backend pattern's `*` matches across `/`.
- **`plan-check`** resolves the tier from the workspace and backend, rejects an unknown `--tier`, refuses state JSON, and with `--trust-config` (the Action's `trust-config`) reads the repository config on a runner.

### MCP and the model judge

- **MCP calls to known infrastructure tools are judged.** In Claude Code and Codex, a call such as the AWS server's `call_aws` or a Kubernetes server's `resources_delete` is judged as the command it is equivalent to. A tool outside the table that carries a shell command is judged as shell, and one that names a guard file as a write to it; other MCP calls are logged and allowed. The table is not tested against the running servers ([docs/mcp.md](docs/mcp.md)).
- **Model judge, opt-in.** A call the rules let through without recognizing anything can be sent to a language model you choose: an OpenAI-compatible endpoint or a program you name. It can only make a verdict stricter, and its block, unlike a rule's, can be approved once. Only the user config turns it on; `applygate check --no-judge` skips it ([docs/judge.md](docs/judge.md)).

### Hosts

- **Claude Code:** a tool applygate does not know whose input carries a command (`Monitor`, `PowerShell`) is judged as a shell call. An ask is shown as a prompt in the default, `bypassPermissions` and auto modes; in `acceptEdits` and `plan` it is enforced as a block. The plugin pins the binary it finds by path and sha256.
- **Codex:** `applygate doctor` says whether Codex will run the hook. Codex skips a hook that is untrusted, or changed since it was trusted, without a message.

### Fixes

- **The decision log** redacts more forms of secret and rotates at 64 MB.
- **The Action** installs with its own `install.sh`, accepts only a release tag as `version`, and keeps plan text from adding outputs or running workflow commands.
- **`check --enforce`** exits by the verdict under observe mode.
- **`init` and `hook install --scope user`** follow `CLAUDE_CONFIG_DIR` and `CODEX_HOME`.
- **The source builds and vets on Windows again** (not a release target).

## v0.5.0 (2026-10-31)

- One-time approvals: `applygate approve [ID]`. On the seven agents that cannot show an ask prompt (and Claude Code in `dontAsk`), an ask used to end as a plain block. The block now names an approval ID; a person runs `applygate approve ID` in their own terminal, types the environment name, and the agent's next identical call is allowed once within 15 minutes (requests expire after an hour). The approval is bound to the agent, session, directory, command and every action's class, environment, tier, workspace, backend, AWS profile and plan SHA-256, so a changed call or plan is judged again. Only asks can be approved; blocks cannot. Without an ID the command lists pending requests. The store is `approvals.json` next to the decision log, a guard path. `approvals: false` in the user or repository config turns it off; a repository config cannot turn it on. Verified end to end with the Codex hook format on macOS: request, wrong word refused, right word approved, one retry allowed, the next one blocked again; not yet tried inside a live agent.
- Guard tampering, found while testing approvals: `script` in its BSD/macOS form (`script -q file command…`) is now unwrapped, so the command it runs is judged; before, `script -q /dev/null <cmd>` hid any command. `expect -c` is analyzed like other interpreters, and code in another language that names an applygate command only a person may run (`approve`, `telemetry on`/`off`, `init`, `disable`, `hook remove`) is guard tampering in every tier.
- `applygate apply` and `applygate approve` check for a terminal with isatty, so stdin from `/dev/null` or another character device no longer counts as one.

## v0.4.0 (2026-10-31)

- Hook adapters for seven more agents, written from each host's documentation and, where it is open source, its source code, and **not tested live**: Cursor (`applygate hook cursor`), GitHub Copilot CLI (`copilot`), Gemini CLI (`gemini`), Windsurf Cascade (`windsurf`), Devin (`devin`), OpenCode (`opencode`, a JS plugin that runs applygate) and Cline (`cline`, an executable `PreToolUse` script). Each reads its host's payload and answers in its documented output format. MCP calls on these hosts are neither inspected nor logged. `applygate hook install --agent NAME [--scope user]` writes each host's own config, `remove` and `doctor` know them all, and `applygate init` names a detected host with the command that installs it but installs only the Claude Code and Codex hooks, which are tested live. `applygate hosts` and `docs/hosts.md` give each host a table whose every cell says "from docs, not tested live" and lists the live tests still pending; the sources are in `review/host-research/2026-10-31-hook-contracts.md`. The scenario pack is replayed in every host's input format (`harness/formats_test.go`, `harness/run.py --format`), and all of them catch every dangerous scenario they can see.
- Claude Code hook loaded by another host: Cursor, Copilot CLI and Devin also run hooks from `.claude/settings.json`, with their own tool names. A shell call named `Shell` or `exec` used to reach `applygate hook claude` as an unknown tool and was allowed; it is now judged like that host's own calls (no ask, a block as exit 2). From those hosts' documentation, not tested live.
- Guard paths: the new hosts' hook configs and scripts (`.cursor/hooks.json`, `.gemini/settings.json`, `.github/hooks/**`, `.github/copilot/settings*.json`, `.copilot/hooks/**`, `.copilot/settings.json`, Windsurf's `hooks.json` files, `.devin/config.json`, `.devin/hooks.v1.json`, `~/.config/devin/config.json`, `.opencode/plugins/**`, `~/.config/opencode/plugins/**`, `.clinerules/hooks/**`, `.cline/hooks/**`, `~/Documents/Cline/Hooks/**`) are protected, so an agent cannot remove or rewrite its own hook.

A `SessionStart` hook fetches it before the first tool call; if no binary can be found, the `PreToolUse` hook exits 2 with the reason, so the tool call is blocked as before. - MCP tool calls are logged, not judged. A Claude Code or Codex tool call named `mcp__<server>__<tool>` is recorded in the decision log with its arguments (compact JSON, secrets redacted like commands, capped at 4 KB) and the note "logged, not judged", and always allowed: in every tier and mode, and also when the repository config is broken (the entry then carries the error). `applygate report` adds a line counting MCP calls per server. The Claude matcher written by `hook install` and the plugin now include `mcp__.*`; `applygate doctor` warns about a Claude hook whose matcher predates it. Other tools applygate does not inspect stay unlogged. Verified live in Claude Code 2.1.312 with a stdio MCP server: the call ran and was logged with its arguments.

## v0.3.2 (2026-10-30)

- Plan gate: fewer false positives from `code-execution` and `exposure`, the two analyzer causes found by the plan-gate false-positive study (`review/fp-study`). `code-execution` flagged every provisioner and `external` data source in the configuration on every plan. It now flags a provisioner only for a resource instance the plan creates, replaces or destroys (a destroy counts because the plan JSON does not tell a destroy-time provisioner from a creation-time one), so a resource at count 0, an empty for_each or a resource the plan leaves alone is no longer reported. It flags an `external` data source only when the plan defers its read to apply; one read during `terraform plan` has already run. Evidence now names the instance (`module.m.null_resource.archive[0]: provisioner local-exec`). `exposure` on an in-place update now reports only exposure the update adds, so a tag change on a security group that was already open to the internet no longer asks; creates and replaces are judged on the planned value as before. On the study's 212 routine plans per tier, protected-tier false positives go from 17 to 0 and every expected prompt is kept; the standard tier stays at 0 prompts.

## v0.3.0 (2026-10-30)

- `applygate suggest`: a proposed `.applygate.yaml` from the observe-mode decision log. Environments come from the directories where the engine ran, with tiers guessed from path names (prod/production/prd/live → protected; staging, stage, uat, qa, non-prod, pre-prod → standard; dev, sandbox, test, examples, demo → disposable) and from hinted workspaces, S3 backends and AWS profiles; directories whose names say nothing stay commented out so strict mode keeps them protected until a person picks; an existing config's environments and settings are kept and not proposed again; every ask or block is listed with the reason it was judged that way. `--root` selects the repository in a shared user log, `--out` writes the file and refuses to overwrite. The output is parsed as a config before it is printed.
- Opt-in telemetry (`applygate telemetry status|on|off|send`, `docs/telemetry.md`). Off by default and in every release. When a person turns it on, one report a day carries the applygate version, OS and architecture, and decision counts per (version, agent, mode, verdict) plus the internal-error count; no commands, paths, names or identifiers. It is built from the local decision log at send time (`status --payload` shows the exact next report), sent from the hook only after the verdict is written and bounded to 3 s, requires https (http only on localhost), follows no redirects, and is forced off by `APPLYGATE_TELEMETRY=0` or `DO_NOT_TRACK=1`. No release carries a default endpoint yet, so `on` needs `--endpoint`; `APPLYGATE_TELEMETRY_ENDPOINT` redirects reports to a collector of your own. An agent running `applygate telemetry on` or `off` is blocked as guard tampering. The decision log reader now folds the pre-rename `seatbelt_version` key into the version, so older logs keep their version counts.
- The plan gate in CI: a composite GitHub Action (`Flurit/applygate@<tag>`, inputs `plan`, `tier`, `fail-on`, `working-directory`, `terraform`, `version`, `binary`), the portable `scripts/ci-plan-check.sh` it runs, and a Terragrunt `before_hook` recipe; documented in `docs/ci.md`. `action-check.yml` exercises the action against two real AWS-provider plans on every push.
- `applygate apply <planfile>`: the human door. Judges a saved plan exactly as the hooks judge `terraform apply <planfile>` (tier, preflight, plan gate), logs the decision with agent `human`, refuses a block, asks for the environment name to be typed back on an ask, and only then runs `terraform` or `tofu` (`--engine`). Outside a terminal an ask is refused unless `--yes`, which never applies in a protected tier.
- Go toolchain 1.26.10. The CI vulnerability scan flags standard-library `net/http` and `crypto/x509` issues in 1.26.7 (GO-2026-6610 to GO-2026-6617, GO-2026-6809) once the binary imports `net/http` for the telemetry sender; 1.26.10 carries the fixes.
